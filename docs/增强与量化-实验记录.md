# 低分辨率增强与量化精度补偿 实验记录

> 2026-11-09 · YOLOv8n @512 · SODA-A ship（train 1253 / val 698，42,428 GT）
> 统一协议：`imgsz=512 epochs=100 batch=16 device=0 seed=0`，评测用 `tools\nwd_eval.py`
> （mAP 用 conf=0.001 / iou=0.45 / max_det=1000；召回列用 conf=0.30）

## 一、结论速览

| 实验 | mAP50 | mAP50-95 | R | 小目标 R(8–16px) | 相对基线 |
|---|---|---|---|---|---|
| 基线（IoU 分配，无增强） | 0.8857 | 0.4783 | 0.8329 | 0.7881 | — |
| NWD 标签分配（α=0.5，最优变体） | 0.8858 | 0.4682 | 0.8467 | 0.8170 | mAP 持平，mAP50-95 −1.0 |
| **低分辨率退化增强（p=0.35）** | **0.8878** | **0.4827** | **0.8513** | 0.7714 | mAP50 **+0.2**、mAP50-95 **+0.4**、召回 **+1.8** |

量化（同一批 20 张 val 图、同一套 letterbox/解码/NMS，`tools\quant_gap.py`）：

| 精度 | kmodel 体积 | mAP50 | mAP50-95 | 相对 fp32 |
|---|---|---|---|---|
| fp32（ONNX） | 12,712,733 B | 0.9260 | 0.5375 | — |
| int8（uint8 PTQ） | 3,634,856 B | 0.9007 | 0.4203 | **−2.53 / −11.73 点** |
| **a16（权重 uint8 + 激活 int16）** | **3,855,680 B** | **0.9279** | **0.5397** | **+0.19 / +0.21 点（无损，且只大 6%）** |
| int16（权重也是 int16） | 12,728,560 B | 0.9261 | 0.5368 | +0.01 / −0.07 点（无损，但体积翻三倍） |

20 类 DIOR @416（40 张 val，`tools\quant_gap_mc.py`）：fp32 0.7718/0.6395 → **a16 0.7753/0.6355（−0.40 点）** vs int8 0.7722/0.5903（−4.93 点），a16 补回 92% 的损失。

**一句话**：两条"免费"路线（改标签分配、加退化增强）都只值 0.2–0.5 个点，属于噪声级；而**只把激活位宽从 8 位换到 16 位（权重仍 int8，体积只涨 6%），就把 −11.7 点的量化损失抹平**。这正面印证了早前的判断——瓶颈在**像素分辨率与量化位宽**，不在标签分配；更准确地说，量化掉点的责任在**激活**（uint8 的 256 级量化），不在权重。

## 二、低分辨率退化增强（`tools\degrade_aug.py`）

### 动机
模型最终看到的是 800×480 摄像头画面缩到 512（0.64×）之后的样子，还叠加了显示屏像素、镜头失焦与 JPEG 压缩；训练集却是干净的 800×800 航拍切片。这个"清晰度域差"是实拍掉点的主因之一。

### 实现
`class RandomDegrade` 四段退化，**全部几何不变**（缩放回原尺寸、不裁剪不旋转），所以框标签不用改：
1. 降采样再放大：`s ∈ [0.35, 0.85]`，`INTER_AREA` 缩小 + `INTER_LINEAR` 放大（模拟传感器分辨率不足）
2. 高斯模糊：70% 概率，`σ ∈ [0.3, 1.2]`（模拟失焦）
3. JPEG 重压缩：50% 概率，`q ∈ [40, 80]`（模拟编码损失）
4. 亮度/对比度抖动：50% 概率，`α ∈ [0.9, 1.1]`、`β ∈ [−12, 12]`（模拟屏幕反光与曝光）

每张图有 `p=0.35` 的概率走完整退化链，插在 `RandomHSV` 之后、几何变换之前。

两个必须知道的工程坑：
- `ultralytics/data/dataset.py:337` 是 `from ... import v8_transforms` 的**绑定名**，只 patch `ultralytics.data.augment` 不生效，必须同时 patch `ultralytics.data.dataset.v8_transforms`。
- ultralytics 8.4.177 的 `v8_transforms(dataset, imgsz, hyp)` **没有 `stretch` 参数**，照抄旧版签名会 `TypeError`。

### 结果与解读
同一协议下 mAP50 +0.21、mAP50-95 +0.44、**整体召回 +1.84 点（0.8329→0.8513）**，但小目标桶召回反而 −1.7（0.7881→0.7714）、tiny 桶 AP 0.0980→0.0826。

说明：退化增强让模型在"糊"的图上更敢报（召回涨），但它没有、也不可能创造分辨率——小目标本来就缺像素，糊化只会让小目标更糊。**所以这条路对"小目标召回"不是解药，只在整体召回上有点收益**。诚实结论：+0.2/+0.4 点属于噪声边缘，不足以单独支撑一个创新点，但可以作为"工程完整性"的一个组件写进方法。

## 三、量化位宽补偿：int8 → int16（本轮最硬的结论）

### 动机
早前实测 int8 量化相对 fp32 掉 −7.0（416）/−11.7（512）点，且换校准算法（Kld）、翻倍校准集（120 张）都只值 0.6–0.7 点 → 判定瓶颈是**位宽**本身。既然 QAT（nncase 的 `UseQAT` 需要 ONNX 里带 QDQ 节点）与逐层混合精度（nncase 2.11 的 `PTQTensorOptions` 只有 `set_tensor_data`，编译器无逐层精度接口）都走不通，那就直接试**整网 int16**。

### 做法
`tools\convert_kmodel.py --a-quant int16 --w-quant int16 --size 512`，其余（NoClip、60 张校准图）与 int8 完全一致，编译 77.2 s。

### 结果
- 体积 3,634,856 B → **12,728,560 B（3.5×）**
- 精度：mAP50 0.9260→**0.9261**（+0.01）、mAP50-95 0.5375→**0.5368**（−0.07）→ **实质无损**
- 对照 int8 同批：0.9007/0.4203（−2.53/−11.73）

这解释了此前的"量化掉点"：**不是校准没做好，而是激活值被压成 uint8（256 级）**。只把权重升到 int16（体积翻倍、6.56MB）几乎没用，mAP50-95 仍是 0.4522（−12.2 点）；只把**激活**升到 int16，体积只涨 6% 就回到 fp32 水平。所以掉点的责任在激活，不在权重——早前把锅算在"权重位宽"上是错的，这里更正。

### 尚未验证（板端要测）
1. **K230 KPU 跑 int16 的速度**——int16 的 MAC 吞吐通常只有 int8 的 1/4，256KB 片上缓存也装不下更大的权重块，可能显著掉帧。
2. **12.1 MB kmodel 能否被 `kpu.load_kmodel` 正常加载**（板子 128MB 内存理论够，但要实测）。
3. 若速度不可接受，退路是"关键层 int16 + 其余 int8"——nncase 2.11 目前没有这个接口，需要改走 QAT 或换 nncase 版本。

## 四、板端实测（2026-11-09，K230D 庐山派 Lite）

测法：与主程序同一套三通道取流（CH0 显示 / CH1 拍照 / CH2 送 AI），60 帧均值，
摄像头对准 2560×1440 的 112 艘船投屏图（画面内约 87 个检出）。

| 配置 | kmodel | 帧率 | 单帧推理 | 平均检出 |
|---|---|---|---|---|
| 512 + int8 | 3,634,856 B | **13.6 fps** | 46.0 ms | 87.1 |
| 512 + **a16** | 3,855,680 B | **11.1 fps** | 64.5 ms | 87.7 |
| 640 + int8 | 3,814,856 B | **10.0 fps** | 73.3 ms | 89.1 |
| 640 + **a16** | 4,142,888 B | **7.9 fps** | 103.5 ms | 78.7 |

三点观察：

1. **a16 的代价是 18% 帧率（512）**，但换回 11.7 个 mAP50-95 点，且体积只涨 6%。
2. **空场景 vs 有目标差距很大**：512 int8 空场景 18.9 fps，87 个框时 13.6 fps——5.3 fps 全花在画框与写标签上（与早前 profiling 的 19 ms 吻合）。这解释了为什么"模型稍慢"时帧率差距会被摊薄（a16 的 46→64.5 ms 只让总帧率降 18%，因为绘图是固定开销）。
3. **a16 让"加分辨率"重新划算**：640 int8 = 10.0 fps，而 512 a16 = 11.1 fps 且精度更高，说明此前"640 太慢不能用"的结论是**int8 量化损失拖累**造成的错觉。

### 640 输入的 a16 也是无损的

| 输入 | 变体 | 体积 | mAP50 | mAP50-95 | 相对 fp32 |
|---|---|---|---|---|---|
| 512 | a16 | 3,855,680 B | 0.9279 | 0.5397 | +0.19 / +0.21 |
| 640 | a16 | 4,142,888 B | 0.9392 | 0.5807 | −0.05 / −0.22 |

（20 张 val、同批同参数；fp32 参考值为同批 onnx 推理。640 的 int8 变体未做同批对拍。）

### 20 类模型（DIOR）也复现了同一个结论

生产环境跑的不是 512 单类，而是 **20 类 DIOR @416**，所以 a16 在 20 类上重做了一遍对拍
（`tools\quant_gap_mc.py`：按类别分别 NMS 与匹配，只统计 GT 数＞0 的类别，40 张 val 图）：

| 变体 | 体积 | mAP50 | mAP50-95 | 相对 fp32 |
|---|---|---|---|---|
| fp32（onnx） | 12,694,920 B（onnx） | 0.7718 | 0.6395 | — |
| **a16**（w uint8 + a int16） | 3,769,280 B | **0.7753** | **0.6355** | **+0.0035 / −0.0040** |
| int8（w uint8 + a uint8） | 3,573,584 B | 0.7722 | 0.5903 | +0.0004 / **−0.0493** |

读法（重要）：

1. **mAP50 在 20 类上几乎没有区分度**——三个变体都在 0.772~0.775，因为 mAP50 只要 IoU>0.5 就算对，
   而 DIOR 里 stadium / tennis / golf 这类大目标本来就饱和在 0.99。**要看 mAP50-95**。
2. 按 mAP50-95 算：int8 掉 **4.93 点**，a16 只掉 **0.40 点**，即 **a16 补回了 92% 的量化损失**，
   与单类 512（−11.73 → +0.21）的方向完全一致。
3. 逐类看，a16 相对 fp32 的变化都在 ±3 点内，没有哪一类被"牺牲"：
   ship −0.026、overpass −0.014、tank −0.007、airport **+0.083**、windmill +0.011、vehicle +0.006。
   （`toll` / `station` 在该 40 张抽样里没有 GT，不计入均值；多个类别饱和在 0.99 的 AP 上限。）
4. 框数：onnx 1964 / a16 1628 / int8 1512。kmodel 框数少不是漏检变多，而是 conf=0.001 时
   int8 的低分尾被压平（分布更"硬"）；**a16 比 int8 多 7.7% 的框**，落点仍是模型多找回来的小目标。

板端同图对照（800×800 的 DIOR 港口图，GT 588 船 + 8 harbor，conf 0.30）：

| 版本 | 检出框 | harbor | ship | 与对方配对 |
|---|---|---|---|---|
| int8 | 522 | 7 | 515 | — |
| **a16** | **561（+7.5%）** | 7 | 554 | 477 对，类别一致 **100%**，IoU 中位 0.716 |

配对 IoU 只有 0.716 **不能**当作"无损"的证据：那张图的船只有 10–15px、彼此相隔 5–10px，
中心差 1px IoU 就掉到 0.8 以下。真正支撑"a16 无损"的是上面第 2、3 条（严格同批对拍 + 逐类不退化）。

**部署推荐**：
- 精度优先 → **640 + a16**：mAP50 0.9392 / mAP50-95 0.5807，板端 7.9 fps
- 平衡（默认） → **512 + a16**：0.9279 / 0.5397，板端 11.1 fps
- 极致帧率 → 512 + int8：13.6 fps，但 mAP50-95 只有 0.4203

```powershell
# 退化增强训练（约 25 分钟）

python tools\train_degrade.py --check          # 先自检增强链
python tools\train_degrade.py model=D:\rs-yolo\weights\yolov8n.pt `
    data=D:\rs-yolo\datasets\sodaa_ship_hbb\data.yaml imgsz=512 epochs=100 `
    batch=16 device=0 seed=0 project=D:\rs-yolo\runs name=aug_deg_512

# 评测（与 NWD 六组同协议）
python tools\nwd_eval.py aug_deg_512

# int16 量化 + 量化损失对拍
python tools\convert_kmodel.py --run D:\rs-yolo\runs\ship_512_v1 `
    --out D:\rs-yolo\runs\ship_512_v1\weights\best_int16.kmodel --size 512 `
    --a-quant int16 --w-quant int16
python tools\quant_gap.py --run D:\rs-yolo\runs\ship_512_v1 --size 512 --n 20 `
    --kmodel D:\rs-yolo\runs\ship_512_v1\weights\best_int16.kmodel `
    --out D:\rs-yolo\runs\quant_gap_512_int16.json
```
