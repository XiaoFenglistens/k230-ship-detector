# 在 128 MB 的 RISC-V 板子上部署 YOLOv8n：我踩过的 21 个坑

> 板子：庐山派 Lite-K230D（K230D，RISC-V C908，128 MB 内存，CanMV / MicroPython 固件），800×480 MIPI LCD。
> 任务：遥感船舶检测。从 DOTA 式旋转框数据一路做到 int8 kmodel，板端 512 输入约 17 fps。

这不是一篇"跑通了"的教程，而是一份**故障目录**：每个坑都写清现象、根因、判据和解法。如果你正在做同类部署，按顺序对一遍能省几天。

---

## 一、环境层（4 个坑）

### 坑 1：清华源装的 torch 是 CPU 版
`pip install torch` 在国内镜像上拿到的是 `2.x.x+cpu`，`torch.cuda.is_available()` 返回 False。CUDA 版必须显式指定索引：`pip install torch --index-url https://download.pytorch.org/whl/cu124`。

### 坑 2：ultralytics 会把 CUDA torch 覆盖回 CPU 版
装 ultralytics 时，它的依赖解析看的是"版本号够不够大"，`2.14.1+cpu` 比 `2.4.1+cu124` 数字更大，于是 pip 认为"已满足"，甚至反向覆盖。**解法**：先装完所有依赖，最后用 `pip install --force-reinstall --no-deps` 装 CUDA wheel，再复验。

### 坑 3：大 wheel 下载会"静默挂起"
下载 2.3 GB 的 torch 时连接不报错、数据不再增长，`--retry` 完全无效。必须加 `--speed-time 20 --speed-limit 102400` 让 pip 主动判定"太慢就断开重连"，配合 `-C -` 续传。

### 坑 4：nncase 的 Windows 版 kpu 插件不在 PyPI
`pip install nncase-kpu` 在 Windows 上装不到（PyPI 只有 manylinux 版），必须去 GitHub release 取 `nncase_kpu-2.11.0-py2.py3-none-win_amd64.whl`。另外 **nncase 与 nncase-kpu 版本必须完全一致**，且 `calibrate_method` 字符串只认 `"Kld"`，写 `"KLD"` 会 `Exception: Unsupported Calibrate Method`。

## 二、数据层（3 个坑）

### 坑 5：OBB 转 HBB 的"无损"需要自证
DOTA 式标注是 8 点旋转框，YOLOv8 检测头吃 5 字段水平框。转换时最怕"悄悄丢框"或"多个旋转框压成同一个正框"。**自证方法**：统计原始标注里的重复行数，再统计转换后的重复行数——本项目 82,007 个框零丢弃，重复行 252（train）/ 10（val）在转换前后完全一致；如果转换引入了重叠，后者的重复行必然更多。

### 坑 6：用 junction / 软链接做数据集目录会被 ultralytics 穿透
Windows 上 `mklink /J` 建的数据集链接，ultralytics 内部 `realpath` 会解析回源目录，于是它读到的是**转换前**的标签，而且不报错。**必须真实复制**。同理 `data.yaml` 的 `path:` 写相对路径会被解析到当前工作目录，必须写绝对路径。

### 坑 7：ultralytics 会强制下载字体，国内直接卡死
首次 `check_det_dataset` 会去 `ultralytics.com/assets/Arial.ttf`（跳到 GitHub）拉字体，超时就 `ConnectionError: Download failure`。把系统 `C:\Windows\Fonts\arial.ttf` 复制成 `%APPDATA%\Ultralytics\Arial.ttf` 与 `Arial.Unicode.ttf` 即可。

## 三、量化层（3 个坑）

### 坑 8：别用 8 张图"看"量化损失
我最早拿 8 张图对比 onnx 与 kmodel 的框数（116 vs 122）和最高置信度（0.846 vs 0.838），看到几乎一致就写了"量化无损"。后来用**同一套** letterbox/解码/NMS 在 60 张验证图上按 mAP 对拍：fp32 0.866 → int8 0.796，**掉 7.0 个点**。框数与置信度是"直观印象"，不是测量。

### 坑 9：换校准算法救不了 int8
Kld 校准 vs NoClip：+0.7 点；校准集 60 → 120 张：+0.6 点。都在 60 张样本的噪声范围内。**瓶颈是权重位宽本身**，要回收只能上 QAT 或混合精度（敏感层 int16）。

### 坑 10：两个 nncase Simulator 不能并行
并行跑两个 `nncase.Simulator` 会静默 `exit 1`，没有 traceback。只能串行；进度写到文件里（stdout 被管道缓冲时看不到）。

## 四、显示与存图（3 个坑）

### 坑 11：`Image.save()` 只支持 RGB565
这是本项目最重要的一条限制。PipeLine 的两路输出——CH0 `YUV420SP`（送屏）与 CH2 `RGBP888`（送 AI）——调用 `save()` 都会得到 `current format not support save function!`。`to_rgb565()` **不是原地转换**，它返回一张新的 Image，原图 format 不变。想存图就必须**另开一条 RGB565 通道**。

### 坑 12：三通道必须在 `sensor.run()` 之前配好
运行后再配 CH1 会 `snapshot chn(1) failed(3)`。正确顺序：`Sensor()` → `reset()` → 三个通道各自 `set_framesize`/`set_pixformat` → `Display.init` → `bind_layer` → `MediaManager.init()` → `sensor.run()`。

### 坑 13：`boot.py` 抢占摄像头且改不动
`/sdcard/boot.py` 优先于 `main.py` 执行，且**在 MicroPython 侧不可修改**（rename 报 `EBUSY 16`、`open('w')` 报 `EPERM`），因为执行时句柄常驻。只能通过 CanMV IDE 的文件面板或读卡器改。如果它是出厂 demo（FHD + 虚拟屏），表现就是"屏幕全黑 + `sensor(2) is already inited`"。解法：换成 4 行 loader，读 `/sdcard/main.py` 后 `exec(_src, {"__name__": "__main__"})`。

## 五、坐标与预处理（4 个坑）

### 坑 14：`display_size` 默认 1920×1080，框会跑到屏幕外
固件 `libs/YOLO.py` 里 `YOLOv8.__init__` 的 `display_size` 默认 `[1920, 1080]`，不显式传 `[800, 480]`，后处理就按 1920 宽度缩放，实测框 x 达到 1368（屏宽只有 800）。

### 坑 15：`config_preprocess()` 必须手动调
`AIBase.__init__` 不调用它，固件里 4 处定义全无调用点。不调则 `ai2d_builder is None`，推理时报 `'NoneType' object has no attribute 'run'`。

### 坑 16：`draw_result` 的签名是 `(res, img)`
传 PipeLine 会报 `'PipeLine' object isn't subscriptable`。正确写法 `yolo.draw_result(res, pl.osd_img)`。

### 坑 17：读图模式下 `ai2d.pad()` 在 packed 布局**不生效**
这是我花时间最多的一个坑。`set_ai2d_dtype(RGB_packed, NCHW_FMT, ...)` 之后，`pad([0,0,top,bot,left,right,0,0], 0, [128,128,128])` 完全没起作用，只有 `resize` 生效——800×480 的图被**直接拉成** 416×416（纵向 ×1.667）。两种参数顺序都不对：NHWC 顺序＝纯拉伸；NCHW 顺序会把 pad 加到别的维度上，画面被压扁。

**判据**：把 PC 侧框按 `y' = (S/H)·y - top` 变换后与板端比，若 IoU 从 0.07 跳到 0.74，就坐实"未 letterbox、纯拉伸"。

**解法**：ai2d 只做等比 resize（`sc = 416/max(W,H)`，`build([1,H,W,3],[1,3,nh,nw])`），padding 改在 numpy 里做；后处理在 416 画布坐标系完成，最后用 `sx=W/nw`、`sy=H/nh` 逆缩放回原图。修完 800×480 上板端与 PC 逐框 IoU 中位 0.073 → **0.744**。

> 而这个 bug **只用正方形图测永远暴露不出来**——正方形不需要 letterbox。这是我后来才想通的。

配套还有两个"一碰就重启"的写法：`np.ones((1,3,416,416))*128`（分配+乘出临时数组）会让板子硬重启；把 ulab 数组直接喂 `kpu.set_input_tensor` 也不行，必须 `nn.from_numpy(canvas)`。

## 六、内存与串口（3 个坑）

### 坑 18：REPL 跑脚本会泄漏到 ENOMEM
`exec(s)` 在 REPL 的 `__main__` 全局命名空间执行，脚本里的 sensor/image 大对象一直挂着，`gc.collect()` 收不掉。正确写法 `exec(s, {'__name__': '__main__'})`，并在 finally 里 `del s; gc.collect()`。一旦 `OSError: [Errno 12] ENOMEM` 出现且 `os.listdir` 全失败，**SD 驱动已进入坏状态，软复位无效，必须物理断电**。

### 坑 19：程序在跑时连串口发 Ctrl-C，会把传感器永久占住
Ctrl-C 打在 finally 里的 `sensor.stop()` 上 → `sensor(2) is already inited` 会跨软复位持续，只能拔 USB 真断电。**停程序只长按 USR 5–6 秒，屏幕变黑再松手**（松早了会被当成短按拍一张）。另外**绝不能发 Ctrl-D**：那是软复位，boot.py 会把主程序重新拉起来。

### 坑 20：串口上传会"返回成功但没写进去"
程序占着串口时，`write_file` 可能返回 `ok=True` 但文件没变。**上传后必须在板上校验** `os.stat(p)[6]` 字节数 + 关键字符串 + `compile(src, name, 'exec')` 三件事，不能信返回值。

## 七、性能（1 个坑，但有反直觉结论）

### 坑 21：画框是第二大开销，且几乎全花在写字上
把一帧拆成六段计时（512 输入、71 个框）：取流 0.9 / ai2d 2.1 / **KPU 40.9** / 后处理 3.6 / **画框 18.9** / 送显 4.9 ms。其中画框那 18.9 ms 里 **16 ms 是 `draw_string_advanced` 逐框写标签**（≈0.24 ms/框）。只画矩形不写字：57.4 ms（16.5 fps）vs 71.3 ms（13.7 fps）——**+20% 帧率**。所以"目标多的时候不显示每个标签"不是美观问题，是性能问题。

## 附：几条能省时间的工位习惯

1. **先测口径再测模型**：同一张图，PC fp32 / 板端 int8 / 不同 letterbox 实现，三者互比能立刻分清"是模型问题还是管线问题"。
2. **评测脚本先在小样本上跑通再上全量**：mAP 计算里一次缓存写错（我把"每张图第一条预测的 IoU 行"缓存给同图后续所有预测用），能算出 mAP50=0.013 却 recall=0.86 的自相矛盾结果。
3. **任何"看起来对"的结论都做一次反向验证**：比如怀疑"烧进图片的红框干扰检测"，就用 A/B 各改一个变量（原图 / 裁放 / 裁放+画框）跑三次，而不是"把红色像素涂灰"这种一次改多个变量的做法（我第一次这么干，把 27% 的像素误判成红色，把图毁掉了）。
4. **把每个数字的出处写进文档**：脚本名、结果文件、样本量、置信度阈值。否则过两周你自己都会混用不同口径。
