# 遥感船舶目标检测 · 庐山派 Lite-K230D 边缘部署

用 YOLOv8n 在 **立创庐山派 Lite-K230D-CanMV**（K230D，128MB 内存）上做船舶检测：
摄像头实时检测 + 按键拍照存 TF 卡，也支持直接把图片文件丢给板子做离线批量检测。

| 项目 | 说明 |
|---|---|
| 板子 | 立创庐山派 Lite-K230D-CanMV（K230D，RISC-V，128MB） |
| 屏幕 | 3.1 寸 MIPI **LCD**（ST7701，800×480），不是 HDMI |
| 摄像头 | GC2093（CSI2） |
| 模型 | YOLOv8n → ONNX → kmodel（nncase 2.11.0），**3.42MB** |
| 数据集 | SODA-A 船舶（ModelScope `lujiajun/sodaa_ship_yolo`），OBB→HBB 转换 |
| 实测 | 摄像头模式 **19.0 fps**，单帧推理 30–35 ms，空闲堆 3.8 MB |

> ### 先看口径（重要）
>
> 这个项目里出现过好几个"精度"，它们**不是一回事**，引用时务必带上口径：
>
> | 口径 | 数值 | 含义 |
> |---|---|---|
> | 同域 val · 电脑 float32 · 416 | mAP50 **0.823** | 训练数据的验证集，未量化 |
> | 同域 val · 电脑 float32 · 512 | mAP50 **0.882** | 同上，更大输入尺寸 |
> | 板端 kmodel · int8 · 416 | mAP50 **≈0.75** | 量化实测掉 6.4~7.0 点 |
> | 跨数据集光学（DIOR） | mAP50 **0.890** | 没参与训练的光学影像，同模态 |
> | 跨模态 SAR（HRSID） | mAP50 **0.192** | 光学模型直接上 SAR，基本不可用 |
> | 真实拍屏端到端（摄像头拍屏幕） | P **0.915** / R **0.887** | 6 帧平均，视野内 71 个 GT，板子静止时 |
> | 多类别（DIOR 20 类）· float32 | mAP50 **0.776** | 单类别换 20 类，证明链路通用 |
> | 多类别 20 类 · 板端 kmodel | 与 PC 逐框一致 | 45 个配对框全部 IoU≥0.5、类别 100% 一致 |
>
> 简单说：**0.919 是 640 同域 float32；板子上跑的是 0.75 左右；换 SAR 就崩；拿摄像头拍屏幕实测还能有 0.887 召回（但要板子稳住，手抖就废）；20 类也跑得通。**

## 一、快速开始

### 场景 1：摄像头实时检测 + 按键拍照（板子离线自跑）

板子上需要有这三个文件（TF 卡根目录）：

```
/sdcard/boot.py        # 4 行启动引导，开机运行 main.py
/sdcard/main.py        # 主程序（= 本仓库 k230_ship_detect.py）
/sdcard/best.kmodel    # 3,581,112 字节
```

上电即自动运行。屏幕左上角看到绿色 `N ships xx.x fps` 就对了。

- **短按 USR**（≥60ms）：拍一张 → `/sdcard/photo/IMG_0001.jpg`，屏幕提示 `SAVED IMG_0001.jpg  69` 保留 2.5 秒
- **长按 USR 3 秒**：退出程序，释放摄像头和显示资源

每按一次会同时写出**三个文件**（结果不再只是"烧进图的像素"）：

| 文件 | 内容 |
|---|---|
| `IMG_0001.jpg` | 带检测框的照片（框烧在像素里，给人看） |
| `IMG_0001.json` | **每个框的精确数据**：序号、开机毫秒、图宽高、帧率、总数，以及逐框 `cls/conf/x/y/w/h`（给程序用） |
| `photos.csv` | 每张照片一行汇总 `seq,uptime_ms,fps,count,file`（Excel 直接打开） |

`IMG_0001.json` 示例：

```json
{"seq": 1, "uptime_ms": 128450, "image_w": 800, "image_h": 480, "fps": 18.7, "count": 2,
 "detections": [{"cls": 0, "conf": 0.843, "x": 614, "y": 495, "w": 28, "h": 22},
                {"cls": 0, "conf": 0.512, "x": 731, "y": 513, "w": 25, "h": 19}]}
```

> 坐标是**左上角式**（原点在图片左上角，x 向右、y 向下），单位像素，已还原到 800×480 画面坐标系。
> 写 JSON 失败不会影响照片保存（异常被捕获，屏幕提示 `SAVE FAILED` 只针对照片本身）。

### 场景 2：把图片文件丢给板子检测（不占摄像头，内存更省）

**一键版**（推荐）：

```powershell
python tools\board_detect_one.py --image D:\path\img.jpg
```

它会自动上传 → 板端推理 → 取回 `DET_img.jpg`（带框）和 `DET_img.json`，并打印检出数与最高置信度样例。

**手动版**：

```powershell
# 1. 把图片传到板子
python tools/k230_repl.py put 图片.jpg /sdcard/input/test.jpg

# 2. 跑检测（板子上 /sdcard/img_detect.py = 本仓库 k230_image_detect.py）
python tools/k230_repl.py run /sdcard/img_detect.py 240

# 3. 取回结果（同名 jpg + json）
python tools/k230_repl.py get /sdcard/photo/DET_test.jpg  D:\rs-yolo\tmp\DET_test.jpg
python tools/k230_repl.py get /sdcard/photo/DET_test.json D:\rs-yolo\tmp\DET_test.json
```

JSON 格式：

```json
{"image_w": 800, "image_h": 800, "count": 118,
 "detections": [{"cls": 0, "conf": 0.853, "x": 637, "y": 438, "w": 38, "h": 28}]}
```

### 场景 3：大图（>850×850，板子内存装不下）

在电脑上切片 → 板子逐张检测 → 电脑合并回原图坐标：

```powershell
python tools/board_batch.py --image D:\path\big.jpg --tile 800 --overlap 100
```

输出 `big_DET.jpg`（画好框的预览）和 `big_DET.json`（合并后的全局坐标，已做跨片 NMS）。

### 环境踩坑（都踩过）

1. **清华源装 torch 得到的是 CPU 版** —— 必须 `--index-url https://download.pytorch.org/whl/cu124`
2. **装 ultralytics 会把 CUDA torch 覆盖成 CPU 版**（版本号比较 `2.14.1 > 2.4.1`）—— 最后再 `--force-reinstall --no-deps` 装回 CUDA wheel
3. **大 wheel 下载会挂起** —— 加 `--speed-time 20 --speed-limit 102400` + `-C -`
4. **pip 往 C 盘 TEMP 解包** —— 设 `PIP_CACHE_DIR=D:\pip-cache`，并在 pip 调用时把 `$env:TEMP` 指到 `D:\pip-tmp`（只对 pip 进程，不改系统变量）
5. **ultralytics 会联网下 Arial.ttf 导致 `check_det_dataset` 失败** —— 把 `C:\Windows\Fonts\arial.ttf` 复制成 `%APPDATA%\Ultralytics\Arial.ttf`
6. **`yolo export format=onnx` 卡死** —— 它在后台 pip 装 onnx 且用默认源。先手动用清华源装 `onnx onnxslim onnxruntime`，再导出（2.8 秒完成）

## 五、训练

```powershell
cd D:\rs-yolo
.\venv\Scripts\yolo.exe detect train model=D:\rs-yolo\weights\yolov8n.pt `
  data=D:\rs-yolo\datasets\sodaa_ship_hbb\data.yaml `
  imgsz=416 epochs=100 batch=16 device=0 workers=4 `
  project=D:\rs-yolo\runs name=ship_416_v1 exist_ok=True plots=True seed=0
```

| 配置 | mAP50 | mAP50-95 | P | R | 训练耗时 |
|---|---|---|---|---|---|
| 416 | 0.823 | 0.408 | 0.841 | 0.771 | 15.8 min（最佳 epoch 99） |
| **640** | **0.918** | **0.536** | **0.897** | **0.863** | 35 min（最佳 epoch 86） |

**640 比 416 多 9.5 个点 mAP50、12.8 个点 mAP50-95、9.2 个点 recall** —— 对这个"目标中位只有 22px"的数据集，输入分辨率就是最有效的杠杆。

**板上实测对比**（同一台摄像头、同一画面、同一张 800×800 图）：

| | 416 | 640 |
|---|---|---|
| 读图检出（该图 GT 105 框） | onnx 118 | kmodel 122 |
| 读图耗时 | 319 ms | 579 ms |
| 摄像头帧率 | **18.4 fps** | 13.4 fps |
| 摄像头平均检出（60 帧均值） | 61.8 | **69.1** |
| 摄像头最高检出 | 71 | **73** |
| 单帧推理 | **32 ms** | 72 ms |
| kmodel | 3,581,112 B | 3,814,856 B |

**结论**：640 在同一画面下**多检出 12%**（61.8 → 69.1 艘），代价是推理时间 2.25 倍、帧率 18.4 → 13.4 fps。密集场景里 416 会漏掉中间几排的相邻小船，640 基本能框全。

对比图：`runs\compare_416_640.jpg`（读图模式）、`runs\compare_camera_416_640.jpg`（摄像头模式）。

**怎么选**：要实时视频/流畅演示用 **416**；要精度、拍静态图或做量化评估用 **640**。切换方法：把 `k230_ship_detect_640.py` 当作 `main.py` 传到板上，并把 `runs\ship_640_v1\weights\best.kmodel` 传成 `/sdcard/best640.kmodel` 即可。

**训练注意点**

- ultralytics 会自动删重复标签（与 `check_duplicates.py` 统计一致，反向验证了转换无损）
- 会自动把 `max_det` 抬到数据集最大目标数（620），否则 recall 被截断
- `weights\yolo26n.pt` 需要手动放到 `D:\rs-yolo\weights\`（AMP 检查会强制下载它，直连 GitHub 只有几 KB/s）

### 量化到底损失多少精度（`tools\quant_gap.py`）

**早先的结论是错的，这里更正。** 最初我只拿 8 张图的框数/置信度比对（同一张图上 onnx 检 116 框 / kmodel 检 122 框，最高置信度 0.846 / 0.838），看到几乎一致就写了"量化无损"——
那是**单个样本的直观印象，不是测量**。真正按 mAP 对拍（60 张 val 图，`conf=0.001`、`max_det=1000`、IoU 0.45，
ONNX(fp32) 与 kmodel(int8) 走完全相同的 letterbox/解码/NMS 代码）：

| | mAP50 | mAP50-95 | 预测框数 |
|---|---|---|---|
| ONNX（float32） | 0.8657 | 0.4533 | 12,425 |
| kmodel（uint8） | 0.7962 | 0.3370 | 11,807 |
| **差** | **−7.0 点** | **−11.6 点** | −618 |

也就是说：**int8 量化让 mAP50 掉了约 7 个点、mAP50-95 掉了约 11.6 个点**。这不是"无损"，是真实的精度代价。
（注意这份 mAP 比 ultralytics 的 val 高，是自写解码/NMS 与原版的细微差异，两边用的是同一套代码，所以**差值可信**。）

这个数字有用，因为它是**可优化空间的上界**。于是我按"最便宜的先试"把它往下压，三档对照（同一批 60 张 val、同一套代码）：

| 方案 | kmodel 大小 | mAP50 | mAP50-95 | 相对 60 张 NoClip |
|---|---|---|---|---|
| NoClip + 60 张校准 | 3,581,112 B | 0.7962 | 0.3370 | — |
| Kld + 60 张校准 | 3,581,152 B | **0.8033** | 0.3347 | +0.7 点 / −0.2 点 |
| NoClip + **120 张校准** | 3,567,424 B | 0.8020 | **0.3384** | +0.6 点 / +0.1 点 |

**结论：换校准算法、翻倍校准集，都只能回收不到 1 个点。** 三档之间的差异已经落在 60 张样本的噪声范围内，
说明**瓶颈不在校准策略，而在权重只有 8 位这件事本身**。要真正把这 7 个点找回来，只能上
量化感知训练（QAT）或对敏感层做混合精度（int16）——这是后续计划里性价比最高的一项。
这也顺便省下了"反复调 PTQ 参数"的无用功。

## 八、实测指标

### 检测精度

- val 集（698 图）：mAP50 **0.823**，mAP50-95 **0.408**，真船检出率 **92%**（混淆矩阵）
- 板上单图（800×800，GT **105** 框）：**118 检出**，319–428 ms/张
- ⚠️ 上面是 **float32** 的精度。板上跑的是 int8 kmodel，实测低约 **7 个点**，见「量化到底损失多少精度」一节。

### 基线对照：为什么不选更大的模型（2026-10-23 补）

同一份数据、同样的训练设置（imgsz=416、100 epoch、batch=16、seed=0），只换网络：

| 模型 | 参数量 | mAP50 | mAP50-95 | Precision | Recall |
|---|---|---|---|---|---|
| YOLOv5nu | ~2.5M | 0.8079 | 0.3953 | 0.8240 | 0.7606 |
| **YOLOv8n（本项目）** | 3.0M | **0.8228** | **0.4080** | 0.8412 | 0.7707 |
| YOLO11n | ~2.6M | 0.8335 | 0.4198 | 0.8415 | 0.7859 |
| YOLOv8s | 11.1M | **0.8721** | **0.4784** | 0.8795 | 0.8211 |

结果 `runs\base_v5nu_416|base_11n_416|base_v8s_416\results.csv`。

**老实说：v8n 不是最优的。**

- YOLO11n 参数量几乎一样，还高 **1.1 个点**；
- YOLOv8s 高 **4.9 个点**，但参数是 3.7 倍、kmodel 大约 12 MB，板上推理会明显变慢、内存也紧张；
- v8n 的定位是「128 MB 板子上能跑满 19 fps 的最大公约数」，不是精度冠军。对外讲的时候要说清楚这是**部署约束下的选择**，不是「我用了最好的模型」。

如果哪天只追求精度（比如换成 K230D 之外有 NPU 更强的板子），第一件事就是把 v8s 或 11n 训到 640 再量化——按上面的数字，天花板大概在 **0.87~0.91**。

### 按目标尺寸分桶的 AP50（`tools\ap_by_size.py`，结果 `runs\ap_by_size_*.json`）

按 800×800 原图上的等效边长 `sqrt(w*h)` 分桶，698 张 val 图全量统计：

| 尺寸桶 | GT 数量 | 416 AP50 | 640 AP50 | 640 增益 |
|---|---|---|---|---|
| tiny <8px | 338 | 0.023 | 0.208 | +18.5 |
| small 8–16px | 12,905 | 0.695 | **0.878** | **+18.3** |
| medium 16–32px | 25,449 | 0.870 | **0.935** | +6.5 |
| large >32px | 3,746 | 0.928 | 0.951 | +2.3 |

**这张表说明 640 的收益 90% 集中在 8–16px 的小目标上**（+18 个点），大目标几乎没有提升（+2 个点）。
也就是说：目标够大时 416 就够用，真正需要 640 的是密集港区里那些十几像素的船。
tiny（<8px）两个模型都做不好（0.02 / 0.21），这是模型的真实能力边界。

### 跨域评测（换一个数据集还准不准）

同域 0.918 只能说明"在自己熟悉的海域里表现好"。为了知道换一片海会不会崩，用两个**完全没参与训练**的外部数据集做了跨域测试：

| 评测集 | 域 | 图片 | GT 框 | mAP50 | mAP50-95 | Precision | Recall |
|---|---|---|---|---|---|---|---|
| 同域 val（SODA-A）· 416 | 同域 | 698 | 42,428 | 0.823 | 0.408 | 0.841 | 0.771 |
| 同域 val（SODA-A）· 640 | 同域 | 698 | 42,428 | **0.918** | **0.536** | 0.897 | 0.863 |
| 跨域光学（DIOR val）· 416 | 跨数据集·光学 | 5,863 | 14,322 | 0.852 | 0.378 | 0.781 | 0.861 |
| 跨域光学（DIOR val）· 640 | 跨数据集·光学 | 5,863 | 14,322 | **0.890** | 0.415 | 0.783 | 0.898 |
| 跨域 SAR（HRSID test）· 416 | 跨模态·SAR | 363 | 1,100 | 0.260 | 0.122 | 0.294 | 0.325 |
| 跨域 SAR（HRSID test）· 640 | 跨模态·SAR | 363 | 1,100 | 0.192 | 0.092 | 0.209 | 0.244 |

图：`runs\crossdomain\crossdomain_compare.png`；明细：`runs\crossdomain\*.json`。
复现：`python tools\eval_crossdomain.py --name <名字> --images <图目录> --coco <COCO json> --model <best.pt> --imgsz 416`

**三条结论（都可以直接写进报告）：**

1. **跨数据集光学几乎不掉**：mAP50 0.852（416）/ 0.890（640），相对同域 100%+。
   说明模型学到的是"船的视觉模式"，不是"记下了 SODA-A 那几片海"。换数据集、换港口、换标注规范都稳。
2. **跨模态（光学→SAR）崩了**：mAP50 只剩 0.26 / 0.19，保留率 32% / 23%。
   SAR 是灰度、有斑点噪声、船是"亮十字"而不是白色船体，模型没见过这个模态。
   这是**真实的能力边界**，不是训练不足——要 SAR 就得拿 SAR 数据重训。
3. **640 不是万能的**：光学上 640 更好（+3.8 点），SAR 上 640 反而更差（−6.8 点）。
   分辨率越高，SAR 的斑点噪声被放大得越厉害。**换域时不能盲目加分辨率。**

> 注意：DIOR 与 DOTA/SODA-A 同属 Google Earth 来源的光学影像，所以这一项是"同模态、跨场景/跨标注集"；
> 真要说"跨传感器光学"（如 Sentinel-2、GF-2），目前的公开可下载数据里还没找到带标注的，等有数据再补。

### 失败分析：错在哪里（`tools\failure_analysis.py`）

光有"精度 0.918"没有说服力，得知道它**在什么情况下会错**。对 200 张 val 图（11,365 个 GT）做逐框归因：

| 指标 | 数值 |
|---|---|
| 预测框总数 | 11,594 |
| TP（对上了） | 9,631（**83.1%**） |
| FN（漏了） | 1,743（**recall 0.847**） |
| FP 贴近某条船（重复框 / 大框套船） | 710（6.1%） |
| FP 远离所有船（纯误报） | 1,253（10.8%） |
| Precision | 0.831 |

**分尺寸召回率**（这才是该看的口径——占比会误导，召回率不会）：

| 目标等效边长 | <8 px | 8–16 px | 16–32 px | >32 px |
|---|---|---|---|---|
| GT 数量 | 6 | 3,308 | 7,055 | 996 |
| **召回率** | **0%** | **72.3%** | **89.4%** | **92.5%** |

图：`runs\failure_analysis\failure_summary.png`；错例总览：`sheet_fn.jpg` / `sheet_fn_small.jpg` / `sheet_fp_near.jpg` / `sheet_fp_far.jpg`。

**四类典型错误（都配了裁剪图）：**

1. **小目标**：8–16 px 区间只召回 72.3%，贡献了全部漏检的 52.5%。<8 px 的 6 个目标一个都没找到。
   这是分辨率决定的，不是训练问题——和前面"按尺寸分桶 AP"的结论互相印证。
2. **密集停靠**：游艇港里船贴船时，模型会输出"一个大框套住一排船"，或者同一艘船出两个框。
   这类占了 710 个 FP（6.1%），特征是"框明显比船大"。
3. **标注漏标（重要）**：随机抽 48 个"远离任何真值"的误报做人工复查，**绝大多数是游艇码头里真实存在、但没被标注的船**。
   也就是说 **precision 0.831 是下界，真实值更高**——这个偏差来自数据集，不是模型。
4. **水上房屋**：浮村场景（如 `00201__800__3250___1300.jpg`）模型报 105 框、只有 18 框有对应标注。
   船屋和水上民居在像素上就是"浮在水上的长条物"，标注口径本身有争议。

> **一个自己踩的坑**（值得记）：第一版脚本用了默认 `max_det=300`，结果漏检最多的三张图预测数都正好停在 300 ——
> 不是模型没看见，是被上限截断了。改成 `max_det=1000`（≥ 本数据集单图最多的 668 个目标）后，
> 同一批图 recall 从 **0.814 → 0.847**，FN 从 2109 → 1743。
> 这和板端 `max_boxes_num` 是同一个坑：**密集场景下，输出上限会直接变成召回天花板**。

### 拍屏端到端：首次逐框定量，并发现一个坐标偏移（`tools\e2e_capture_eval.py`）

做法：给板端起一次"干净存图"（`k230_ship_detect_512_cap.py`，按下 USR 时在画框**之前**另存一张 `CAP_xxxx.jpg`），照片与同帧的 `IMG_xxxx.json`（逐框坐标）配对；PC 端用 SIFT + RANSAC 求"照片 → 原图"的单应性，把原图 GT 投影到照片坐标系，再与板端输出按 IoU≥0.5 贪心匹配。

- 照片视野覆盖原图 **21.0%**（四角映射到源图 (451,145)–(859,479)），视野内 GT **68** 个、板端输出 **70** 框。
- 直接匹配结果：**TP 12 / FP 58 / FN 56**（P 0.171、R 0.176）。这个数字不能用。
- 交叉检查找到原因：**板端框坐标有系统性平移**。同一张干净照片上，板端 70 框与 PC 模型 70 框**数量相同、尺寸一致**（宽比 1.01、高比 0.98），但把板端框整体平移 **(−17, +4) px** 才能对齐，平均 IoU 从 0.406 升到 0.737；用 GT 侧独立复算得到一致的 **(−19, +3) px**。
- 平移补偿后：TP 67/68、P 67/70=0.957、R 0.985、平均匹配 IoU 0.724。

**结论（诚实版）**：补偿后的 0.985 是**在同一批数据上拟合平移量**得到的，属于乐观估计，不能当成绩写；但它证明了管线本身没坏，真正的缺陷是**板端框相对图像有约 18 px 的水平偏移（约为 800 宽度的 2.3%）**，画在屏上同样偏。成因未定位，两个候选：① ai2d letterbox 的 pad 反向映射；② CH1（拍照）与 CH2（送 AI）两路 ISP 输出的窗口差异。下一步用 416 模型跑同一场景看偏移量是否随输入尺寸变化——不变则指向 ISP 通道差异，按比例变则指向 letterbox 映射。

> **上面这段的"缺陷"结论是错的，2026-10-25 已查清并更正**：不是坐标 bug，是**按键时板子在动**（手举着拍的）。真正的映射误差只有 1~2 px，详见下面第三节。

#### 2026-10-25 追查：两个新结论

**一、读图模式对非正方形输入是错的（真 bug，自己的代码）——当天已修复并验证。**

把一张 800×480 的裁剪图（`tmp\crop800x480.jpg`，取自 val `00063` 下半部分）喂给板子读图检测，与 PC 同图同 416 逐框比：板端 98 框 / PC 92 框，但每框最佳 IoU 中位只有 0.073，只有 12% 的框 >0.5；板端框中位 **28×31**，PC 中位 **26.7×20.4** —— 高度被放大了约 1.5 倍。

把 PC 的框按 `y' = 1.6667·y − 160`（竖向拉伸 800/480、再减去 letterbox 的 160 像素）变换后重新比较：**中位 IoU 0.742、均值 0.718、96% 的框 >0.5**。也就是说模型看到的是**把 800×480 直接拉伸成正方形**的图，`ai2d.pad()` 在 `RGB_packed`（NHWC）布局下**没有生效**，只有 `resize` 起作用；尺寸为正方形（800×800）的图恰好不受影响，所以早前用方形遥感图测试时一切正常。
换成 NCHW 顺序 `[0,0,0,0,top,bot,left,right]` 再试：34 框、框高中位只有 9 px，被压扁，同样不对。

**修法（`D:\rs-yolo\k230_image_detect.py`，已改并上板验证）**：不再依赖 `ai2d.pad()`，改成两段式——
1. ai2d 只做**按比例**缩放：`sc = 416/max(W,H)`、`nw/nh` 等比、`left/top = (416-nw/nh)//2`，`build([1,H,W,3],[1,3,nh,nw])`；
2. numpy 里补灰边：`canvas = np.zeros((1,3,416,416), uint8)`，四条 pad 带填 128，再把 `small` 贴进 `top:top+nh, left:left+nw`；
3. 后处理在 416 画布坐标系里做，再统一换算回原图：`sx = W/nw`、`sy = H/nh`，框变 `((x-left)*sx, (y-top)*sy, w*sx, h*sy)`，`left=top=0` 传给画框/写 JSON。

两个不能用的写法（都试过，会把板子搞崩或算错）：
- `np.ones(...) * 128`（分配 + 乘出临时数组）会把板子搞到硬重启；**必须 `np.zeros` 分配后分区赋值**；
- 把 ulab 数组直接喂 `kpu.set_input_tensor` 也不行，**必须 `nn.from_numpy(canvas)`**。
另外 `ai2d.run()` 返回的是 `runtime_tensor`，**没有 `.shape`**，只有 `.to_numpy()`。

修复后实测（板端 vs PC 同图同 416，逐框最佳 IoU）：

| 输入 | 板端框数 | PC 框数 | IoU 中位 | >0.5 占比 | 修复前中位 |
|---|---|---|---|---|---|
| 800×480 非方图 | 95 | 92 | **0.744** | **96%** | 0.073 |
| 800×800 方图（回归） | 121 | 115 | **0.679** | **90%** | 0.679（不受影响） |

生产脚本直接上板跑通：800×800 → 121 ships / 392 ms，800×480 → 95 ships / 291 ms，`DET_*.jpg` 目视红框逐船命中。

**二、摄像头那 18 px，可能根本不是坐标 bug，而是手抖。**

三条参照（GT 单应性投影、PC 模型、板端自绘）**都锚在 CH1 拍的那张照片上**，而框来自 CH2 那一帧。程序里是先 `snapshot(chn=CH2)` 推理、按下 USR 时再 `snapshot(chn=CH1)` 存图——两次取帧之间隔了几十毫秒。板子当时是手举着的，几十毫秒的手抖足以让 800 像素宽的视野平移 18 px（2.3%）。
所以"补偿后 0.985"和"2% 缩放"更可能是**两通道的时间差**，而不是映射错误。判据很简单：把板子放在桌上（完全静止）再拍一次，如果偏移消失 → 是手抖；如果仍是 (−18,+4) 且稳定 → 才是坐标 bug。

**三、查清了：不是坐标 bug，是按键把板子推动了；顺带拿到了第一份可信的拍屏端到端指标。**

做法（`k230_ship_detect_512_auto2.py` + `tools\e2e_auto_analyze.py` + `tools\e2e_auto_gt.py`）：改成**按一下 USR 才开始连拍**，按下后先等 2 秒（让按键引起的晃动衰减），再每 0.7 秒存一对干净图 `AUTO_xx_a.jpg` / `AUTO_xx_b.jpg`（各配一份逐框 json），共 6 对。`a` 紧跟在推理帧之后取，`b` 是隔一次 JPEG 编码后再取一张——**a 与 b 之间没有任何模型参与，它们之间的位移就是板子自己的抖动**。

| 检查项 | 结果 | 含义 |
|---|---|---|
| a → b 位移（相位相关） | **0.0 ~ 0.6 px**，相关度 0.94~1.01 | 这 6 对拍摄期间板子基本没动 |
| 板端框 vs PC 框（零平移） | 平均 IoU **0.79~0.84** | 框与图像天然对齐 |
| 板端框 vs PC 框（最佳平移） | **(+1, +1) px**，IoU 0.83~0.85 | 映射误差只有 1~2 px |

对照昨天那张：同样的代码重算 `CAP_0005` 仍然是 **TP 12**（说明不是脚本 bug），但那批是**手举着板子、按键瞬间拍的**；今天把板子放在水杯上，同样用"按键拍"得到的 `CAP_0006/0007/0008` 却是 R **0.887 / 0.887 / 0.803**。**差别不在代码，在板子稳不稳。**

**拍屏端到端指标（6 帧平均，512 模型，视野内 71 个 GT）**：

| | TP | FP | FN | P | R | F1 | 平均匹配 IoU |
|---|---|---|---|---|---|---|---|
| **自动连拍 6 帧（板子静止）** | 378 | 35 | 48 | **0.915** | **0.887** | **0.901** | **0.799** |
| 按键拍 3 帧（手扶） | 183 | 28 | 30 | 0.867 | 0.859 | 0.863 | — |

逐帧非常稳：TP 每次都正好 **63/71**，FP 4~7 个，FN 8 个（这 8 个漏检在 6 帧里完全一致，是该视野里的固定漏检，不是随机噪声）。

**像素账**（解释为什么拍屏召回这么高）：视野内 GT 目标中位 **41.9 px**（p10 28 / p90 54），缩到 512 输入后约 **27 px** —— 远高于降质实验里"12 px 开始掉"的门槛，所以检出率不降反升。
**同时正式作废早前"拍屏保留率只有 58%"的说法**：那个数字来自手抖的照片 + 拿整张源图的 105 框做分母，两处都错。

### 一帧的时间花在哪：速度分解（`tools\profile_plot.py`，图 `runs\profile_breakdown.png`）

把一帧拆成六段分别计时（板端每档 60 帧取均值）：取流 `snapshot` → 预处理 `preprocess`（ai2d letterbox）→ `inference`（KPU）→ `postprocess`（解码+NMS）→ `draw`（画框+标签）→ `show`（送显）。

| 场景 | 取流 | 预处理 | **KPU** | 后处理 | **画框+标签** | 显示 | 合计 | fps |
|---|---|---|---|---|---|---|---|---|
| 416 · 70 框 | 3.3 | 1.7 | **28.8** | 2.4 | **19.2** | 4.8 | 60.1 ms | 16.2 |
| 512 · 71 框 | 0.9 | 2.1 | **40.9** | 3.6 | **18.9** | 4.9 | 71.3 ms | 13.7 |
| 512 · 68 框（只画框不写字） | 2.7 | 2.2 | **41.3** | 3.0 | **2.7** | 5.5 | 57.4 ms | **16.5** |
| 512 · 空场景 | 3.9 | 2.3 | 41.3 | 1.1 | 0.5 | 4.6 | 53.7 ms | 18.3 |
| 416 · 空场景 | 15.4 | 1.7 | 28.0 | 0.7 | 0.5 | 5.7 | 52.1 ms | 18.8 |

（单位 ms/帧；`snapshot` 是阻塞等下一帧，数值抖动大属正常，不代表计算成本。）

三条结论：

1. **KPU 推理是大头但不是唯一大头**：占 48%（416）/ 57%（512）。512 的推理耗时 40.9 ms 是 416 的 1.42 倍，接近面积比的 1.51 倍——说明算力开销基本按像素线性增长。
2. **画框是第二大开销，而且几乎全是"写字"**：70 个框时 `draw` 要 19 ms，占 27–32%；同样 68 个框**只画矩形不写标签就只要 2.7 ms**——16 ms 全花在 `draw_string_advanced` 逐框渲染文字上（约 0.24 ms/框）。
   → 这解释了主程序为什么在目标数超过 `LABEL_LIMIT=25` 时只画框不写字：**那不是为了画面干净，是实打实的帧率优化**，实测潜在收益 +2.8 fps（13.7 → 16.5，+20%）。
3. **其余环节都很便宜**：ai2d 预处理只有 1.7–2.3 ms（硬件加速），后处理 1–4 ms，送显稳定 5 ms 左右。想再提速只能动模型规模/输入尺寸，而不是优化 Python 循环。

可继续优化的方向（按收益排序）：① 标签只在框够大或置信度够高时画（已部分实现）；② `show` 若可接受轻微撕裂，可改成隔帧刷新；③ 后处理 3 ms 属可接受范围，不值得动。

### 精度-速度帕累托曲线：该选哪个输入尺寸（`tools\pareto_plot.py`）

四个输入尺寸各训练 100 epoch、各自量化成 kmodel、都在同一块板子同一场景下测速（摄像头对着全屏船港图，每档跑 60 帧、每 4 帧 `gc.collect()`，框数 62~70 接近，口径一致）：

|---|---|---|---|---|---|
| 320 | 0.7004 | 0.3038 | 3.32 MB | 18.3 fps | 22.2 ms |
| **416（部署默认）** | **0.8228** | **0.4080** | 3.42 MB | 16.2 fps | 33.8 ms |
| **512** | **0.8816** | **0.4771** | 3.47 MB | 13.8 fps | 47.4 ms |

图：`runs\pareto_curve.png`，数据：`runs\pareto_table.json` + `runs\pareto_board.json`。

三条结论：

1. **320 不划算**：帧率只比 416 高 2.1 fps，mAP50 却掉 12.2 个点——128 MB 的板子完全跑得动 416，没有理由降分辨率。
2. **512 是拐点（性价比最高）**：比 416 只慢 2.4 fps，mAP50 +5.9 点、mAP50-95 +6.9 点，模型只大 0.05 MB。**如果能接受 13~14 fps，512 是比 416 更好的部署选择。**
3. **640 是精度上限但代价陡**：比 512 再 +3.6 点，但帧率掉到 10.1 fps、推理 74 ms。适合"只拍单张/对准后按键存图"的场景，不适合实时预览。

> 口径说明：本表的帧率是**统一测速脚本**（`tmp\bench5_*.py`，自建三通道 + 每 4 帧 gc）测出的，
> 比主程序屏幕右上角显示的值**低约 3 fps**（主程序每 30 帧才 gc 一次）。
> 横向比较看这张表；**绝对值看主程序实测**：416 → 19.0 fps、**512 → 17 fps（同场景 70 艘船）**、640 → 13.2 fps。
> 两者差值稳定在 3 fps 左右，说明这套 bench 是可靠的**相对**测量工具，绝对值偏保守。
> 另：640 若不周期 gc 会直接 `ndarray malloc fail`（ai2d 输出 640×640×3=1.23 MB + snapshot 视图 1.15 MB 把 3.8 MB 堆撑爆），这是 640 档必须每 4 帧回收的原因。

### 拍屏正交实验：距离 × 视角 × 光照怎么影响检出（图 `runs\orth\orth_curve.png`）

> 上一版这里写的是「真实拍屏的端到端定量：为什么这里没有这个数字」，那一版已被
> 上面「拍屏端到端」一节取代（数字做到了：P 0.915 / R 0.887 / F1 0.901）。
> 本节是在那之后补的第二组实验：不再只测一个点，而是**换着拍摄条件测 8 个格**。

**做法**：屏幕（2560×1440）显示 `D:\rs-yolo\orth_screen.png`——源图 800×800 缩到 1440×1440 居中、左右补黑边，
避免「远」档视野里拍到源图之外的东西（那些区域会被当成误报）。板子跑 `k230_ship_detect_512_orth.py`：
按一次 USR 开一组，自动连拍 3 对（`ORT_<组>_<对>_a.jpg` / `_b.jpg` / `.json`），再按一次进下一组，屏幕上显示当前组号。
8 组 = 距离（近/远）× 视角（正对/偏斜约 30°）× 光照（开灯/关灯）。

变量不靠"我觉得"，全部有客观量：

| 想控的 | 客观指标 | 怎么算 |
|---|---|---|
| 距离 | 画面里目标的中位边长 px | GT 四角经单应性投到照片上取中位边长 |
| 视角 | 投影四边形左右边长比 | 1.0 = 正对，越小越偏 |
| 光照 | 画面平均亮度 | 灰度均值 |
| 拍稳没 | a→b 位移 | `cv2.phaseCorrelate` |

**先剔除「按下那一瞬间」**：每组第 1 对的 a→b 位移中位 **27.4 px**，第 2、3 对只有 **1.9 px**；
对应召回 0.112 vs 0.244。**按键这个动作本身会让画面在 2 s 内继续晃**，程序里 `AUTO_SETTLE_MS=2000` 不够。
下面所有统计只用第 2、3 对（每组 GT 210）。

| 组 | 距离 | 视角 | 光照 | 目标 px | 亮度 | 倾斜比 | 抖动 px | R | P | F1 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 近 | 正对 | 开灯 | 14.2 | 77.0 | 0.984 | 2.27 | 0.367 | 0.374 | 0.370 |
| 2 | 近 | 正对 | 关灯 | 14.4 | 74.7 | 1.017 | 1.64 | **0.605** | 0.583 | 0.594 |
| 3 | 近 | 偏斜 | 关灯 | 13.2 | 75.3 | 0.771 | 3.31 | 0.138 | 0.151 | 0.144 |
| 4 | 近 | 偏斜 | 开灯 | 12.2 | 71.3 | 0.656 | 2.08 | 0.233 | 0.274 | 0.252 |
| 5 | 远 | 正对 | 开灯 | 11.2 | 67.4 | 1.010 | 1.78 | 0.300 | 0.453 | 0.361 |
| 6 | 远 | 正对 | 关灯 | 11.1 | 58.0 | 0.975 | 5.06 | 0.133 | 0.200 | 0.160 |
| 7 | 远 | 偏斜 | 开灯 | 9.3 | 64.1 | 0.660 | 2.32 | 0.148 | 0.333 | 0.205 |

**边际效应（按 GT 加权）**

| 因素 | 两个水平 | 倍数 | 读法 |
|---|---|---|---|
| 视角 | 正对 **0.351** / 偏斜 0.137 | **2.6×** | 最贵的变量 |
| 距离 | 近 **0.336** / 远 0.152 | 2.2× | 本质是目标像素 |
| 光照 | 开灯 0.262 / 关灯 0.226 | 1.2× | **无效，见下面第 3 条** |

交叉看更清楚：近/正对 0.486、近/偏斜 0.186、远/正对 0.217、远/偏斜 0.088。

**四条结论，其中第 3 条是这次没做成的地方**

1. **偏 30° 就掉六成**：同样是近距，正对 0.486 → 偏斜 0.186；远距 0.217 → 0.088。透视压缩让船变窄变斜，
   而训练集是正射影像（几乎无透视），这是**分布外**。实测建议：拍屏幕尽量正对，偏移角度 <15°。
2. **目标像素仍是主因**：13.9 px → 0.370、11.5 px → 0.222、9.3 px → 0.148、8.6 px → 0.029，
   与「拍摄条件 → 检出率」的模拟曲线同方向，但**真实拍屏掉得更快**（模拟 8.8 px 还有 0.645，实测 8.6 px 只有 0.029）——
   因为真实链路还叠了摩尔纹、重采样、失焦、曝光，这些模拟里没有。
3. **光照这一维失败了**：组 1（开灯 77.0）与组 2（关灯 74.7）亮度只差 2.3，召回却 0.367 vs 0.605，
   方向还与"越亮越好"相反。合理解释是**关灯没真的把画面变暗**（屏自身亮度占主导），或组 1 作为全场第一组
   相机还没稳定。**所以这一维不能当结论用**；要重做得关房间灯 + 固定曝光（或加中性密度片）。
4. **不能跨实验比绝对值**：这次整屏显示只有 8.6~14.4 px，而之前那次演示图把船放大到 **41.9 px**，
   所以 0.887 与这里的 0.15~0.6 不是"退步"，是**目标像素完全不同**。横比只能在同一实验内部做。

**实验局限（这两条必须写在明处，否则别人复现不出同样的数）**

1. **没有固定支架，全靠手扶**。板上所有拍屏数据，板子要么手举、要么垫在水杯上用手按住，**没有三脚架/夹具**。
   直接后果：① 每按一次 USR，机身都会动，所以每组"按下那一瞬间"的那一对必须剔除（实测前后位移中位 **27.4 px**，
   稳定对只有 1.9 px）；② 即使判定为"稳定"的对，前后两张仍有 1–5 px 残余位移，这部分会摊到平均匹配 IoU 上
   （实测 0.799，纯算法层面应更高）；③ 距离与角度靠目测控制，实际角度在 ±5°、距离在 ±10% 内浮动，
   所以本文的角度/距离效应用**客观量（目标像素、投影边长比）**做横轴，而不是用"近/远、正对/偏斜"这几个字。
   要复现，先解决支架问题；用夹具把板子固定后，同一批数据的 IoU 与召回都会更好看，但那不是同一个实验。

2. **屏幕亮度与环境光没有控住，且会直接影响结果**。屏幕本身是自发光的强光源，手机/相机对着它拍时
   自动曝光与自动增益会随画面内容变化；再叠上室内灯的色温与照度，同一张图在不同亮度下拍出来的
   噪声、对比度、摩尔纹强度都不同。本次"开灯/关灯"这一维就没做成——两组画面平均亮度只差 2.3 个灰度
   （77.0 vs 74.7），说明**关灯并没有真正降低画面亮度**（屏幕自发光占主导），结果反而出现方向相反的偏差
   （0.367 vs 0.605），所以**光照维度不作为结论**。要重做必须：关掉房间灯或加遮光筒、把屏幕亮度锁死、
   相机端固定曝光与增益（关自动曝光）。在此之前，"光照对检出率的影响"在本项目里是**空白**，不是"影响很小"。

- `write_json` 里给每条检测加了 `"name": "%s"` 占位符却没给对应实参 → `TypeError: format string needs more arguments`，每条图都失败但 jpg 已经写出（画框在前、写 JSON 在后），现象有迷惑性。已修。
- 板端 `write_file` 返回 `ok=True` 但**内容没写进去**（串口被运行中的程序占用时会发生）。必须写完后在板上 `os.stat` 校验字节数 + 关键字符串 + `compile()`，不能信返回值。

## 九、踩坑清单（板端，都是实测撞出来的）

### 显示与存图

1. **`Image.save()` 只支持 RGB565** —— YUV420SP / RGBP888 / RGB888 / ARGB8888 全报 `current format not support save function!`
2. **`to_rgb565()` 不原地转换**，返回新 Image
3. 所以拍照必须给 sensor 单开一条 `set_framesize(800,480) + Sensor.RGB565` 通道 —— 最终是**三通道**：
   - CH0 `YUV420SP` → `Display.bind_layer(..., LAYER_VIDEO1)`，只送屏，不过 CPU
   - CH1 `RGB565` → 专门存图
   - CH2 `RGBP888` → 给 AI（planar CHW）
4. **三通道必须在 `sensor.run()` 之前全部配置完**，之后再配会 `snapshot chn(1) failed(3)`
5. `Display.show_image()` 不能显示压缩 JPEG（`unsupport image format 101056512`），要先 `to_rgb888()`/`to_rgb565()`

### YOLOv8 高层模块

6. `libs.YOLO.YOLOv8` 的 `display_size` 默认 **[1920,1080]** —— 不显式传 `[800,480]`，框坐标会按 1920 缩放（实测 x 到 1368，远超屏宽）
7. **`config_preprocess()` 必须手动调用** —— 固件里 4 处定义都没有调用点，不调用则 `ai2d_builder` 为 None，报 `'NoneType' object has no attribute 'run'`
8. `draw_result` 签名是 `(res, img)`，不是 `(pl, res)`
9. `max_boxes_num` 默认 50，要显式传（本项目设 200）

### GPIO

10. `machine` 模块**没有 `fpioa`**，`FPIOA` 是类：
    ```python
    from machine import Pin, FPIOA
    fpioa = FPIOA()
    fpioa.set_function(64, FPIOA.GPIO64)
    ```
11. USR 按键（Lite 版）= **GPIO64**（非 Lite 版是 53），`Pin.PULL_DOWN`，**按下为 1**；RGB 灯红 GPIO65 / 绿 GPIO66

### 内存与启动

12. **REPL 里 `exec(s)` 在共享 globals 跑脚本会泄漏内存**，直到 `ENOMEM` —— 必须 `exec(s, {'__name__': '__main__'})` 并 `gc.collect()`
13. **SD 驱动在内存耗尽后会进坏状态，必须物理断电**才能恢复（软复位没用）
14. **`boot.py` 优先于 `main.py` 执行，且在 MicroPython 侧改不了**（rename/remove 报 EBUSY、`open('w')` 报 EPERM，因为句柄常驻）—— 只能通过 CanMV IDE 文件面板或读卡器改
15. **RESET 键是软复位**，Sensor/ISP 的 C 层状态不释放，"already inited" 会跨软复位持续，**卡住就拔 USB 真断电**
16. 在程序运行时按 Ctrl-C 可能打断 finally 里的 `sensor.stop()`，导致传感器永久占用 —— 正常退出请**长按 USR 3 秒**
17. `os.path` 在 MicroPython 里**不存在**（`AttributeError: 'module' object has no attribute 'path'`），用 `os.stat` + try/except
18. `str.endswith` **不接受 tuple**，要逐个判断

### 板端读图（img_detect.py）

19. `image.Image("xxx.jpg")` 能载入（format=JPEG），但 `to_numpy_ref()` 报 `image format not support`；**先 `to_rgb888()` 就能拿到 (H,W,3) uint8**
20. ai2d 支持 **RGB_packed** 输入：`set_ai2d_dtype(RGB_packed, NCHW_FMT, np.uint8, np.uint8)`，build 输入形状写 `[1,H,W,3]`
21. 板子 MicroPython 堆约 3.8MB，800×800 图载入后只剩 ~2.0MB；**>850×850 会 OOM**，大图请用 `tools\board_batch.py` 切片
